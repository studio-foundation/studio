# Plan — STU-1653: Let a pipeline pause between stages for a human to approve or edit a stage's output

Path: fallback (no shaping bundle; planned directly from the issue + code research)
Scope: a stage-level `approval` YAML key that pauses after a stage succeeds, lets an
interactive run approve/edit the output via a new `reviewStageOutput` engine callback
(mirroring `askHuman`), substitutes the (possibly edited) output back into pipeline
context, and logs both the original and resolved output. Non-interactive behavior is
configurable per stage (`on_unavailable: fail | auto-approve`, default `fail`), so it
never hangs.

Insertion point decided with the user: inside `StageExecutor.execute()`
(engine/src/pipeline/stage-executor.ts), not engine.ts — confirmed by grep that
`group-orchestrator.ts` calls the same `stageExecutor.execute()` instance, and map/call
child engines are built with the same `EngineConfig` object, so this one insertion point
covers simple stages, group stages, and map/call child-pipeline stages with zero
per-orchestrator duplication.

## Changes

1. Add `StageApprovalConfig` type and `approval?: StageApprovalConfig` field to
   `StageDefinition` — `contracts/src/pipeline.ts`, sibling to `hooks?: StageHooks`.
   ```ts
   export interface StageApprovalConfig {
     on_unavailable?: 'fail' | 'auto-approve';  // default: 'fail'
   }
   ```

2. Parse and strict-check the new `approval` block — `engine/src/pipeline/loader.ts`.
   - Add `'approval'` to `STAGE_FIELDS`.
   - Add `const APPROVAL_FIELDS = ['on_unavailable'] as const`.
   - `checkStageFields()`: `checkBlock(stage.approval, APPROVAL_FIELDS, ...)`, plus a
     value check that `on_unavailable` (if set) is `'fail'` or `'auto-approve'`.
   - New `parseApprovalConfig(entry)` mirroring `parseStageHooks()`: returns `undefined`
     when `entry.approval` is absent, else `{ on_unavailable: entry.approval.on_unavailable ?? 'fail' }`.
   - Wire into both stage-construction sites: the simple-stage push (~line 185) and the
     group's inner-stages `.map()` (~line 179) — both need `approval: parseApprovalConfig(s)`.

3. New event type — `engine/src/events.ts`, placed near `HookAskEvent`/`onHookAsk`:
   ```ts
   export interface StagePauseEvent {
     stage_name: string;
     original_output: unknown;
     resolved_output: unknown;
     decision: 'approved' | 'edited' | 'auto_approved' | 'failed';
   }
   ```
   Add `onStagePause?: (event: StagePauseEvent, ctx?: EventContext) => void;` to
   `EngineEvents`. No change needed to `createTaggingAdapter` — it's a generic Proxy.

4. `EngineConfig.reviewStageOutput` — `engine/src/engine.ts`, sibling to `askHuman`:
   ```ts
   reviewStageOutput?: (stageName: string, output: unknown) =>
     Promise<{ decision: 'approved' | 'edited'; output: unknown }>;
   ```
   Pass it through to the `StageExecutor` constructor call (~line 192, alongside `askHuman: config.askHuman`).

5. `StageExecutorConfig.reviewStageOutput` (same signature) — `engine/src/pipeline/stage-executor.ts`.
   In `execute()`, insert a new phase right after the `on_stage_complete` hooks block
   (after line 588) and before "Finalize task run" (line 590):
   - Only runs when `stageStatus === 'success' && stageDef.approval`.
   - `reviewStageOutput` present (interactive run): await it with `(stageDef.name, originalOutput)`,
     emit `onStagePause` with the decision it returned, then mutate
     `ralphResult.result.output = review.output` — the existing finalize code at lines
     590-640 (`lastResult`, `stageRun.output`, `onStageComplete`'s `output` field, the
     returned `lastAgentOutput`) already reads through `ralphResult.result` unchanged, so
     the edited value flows to context propagation with no further edits needed.
   - `reviewStageOutput` absent (non-interactive): apply `stageDef.approval.on_unavailable`
     — `'auto-approve'` emits `onStagePause` with `decision: 'auto_approved'` and leaves
     output untouched; `'fail'` (default) sets `stageStatus = 'failed'` and emits
     `onStagePause` with `decision: 'failed'`, following the exact same inline
     `stageStatus = 'failed'` pattern the `on_stage_complete` hook block already uses
     (lines 574-581) — never hangs.

6. CLI wiring — `cli/src/commands/run.ts`.
   - Add `reviewStageOutput` to the `engineConfig` object, inside the same
     `process.stdin.isTTY && process.stdout.isTTY && !options.json` conditional spread
     that already gates `askHuman` (~line 599-613), reusing the same `askQueue` chain and
     `progress.withSpinnersPaused()` wrapper for serialization.
   - Implementation: print the stage output, `confirm()` "Approve as-is?" (default true);
     on no, `editor()` (from `@inquirer/prompts`, already a dependency) pre-filled with
     `JSON.stringify(output, null, 2)`; `JSON.parse` the result, falling back to the raw
     edited string if it doesn't parse (output stays `unknown` to the engine either way).
   - `mergeEvents()`: add an `onStagePause` handler mirroring the existing `onHookAsk` one
     (~line 278-286) — forwards to `progressEvents.onStagePause` and writes a
     `stage_pause` JSONL line via the `log()` helper (fields: `stage`, `original_output`,
     `resolved_output`, `decision`) — `redact()` already runs on every `logger.log()` call
     so no extra PII handling needed.

7. Engine-level tests:
   - `engine/src/pipeline/loader.test.ts` — parsing/validation of the new `approval` block
     (present/absent, invalid `on_unavailable` value, default fill), mirroring the existing
     hook-parsing tests in that file.
   - `engine/tests/unit/engine.test.ts` — run a two-stage inline pipeline (mock provider)
     where stage 1 has `approval:`. Cases: `reviewStageOutput` returns `{ decision: 'edited', output }`
     → downstream stage's `previous_stage_output` context shows the edited value, and
     `onStagePause` fires with both original and resolved output; no `reviewStageOutput` +
     `on_unavailable: auto-approve` → succeeds with the original output and
     `decision: 'auto_approved'`; no `reviewStageOutput` + `on_unavailable: fail` (default)
     → stage status `failed`, pipeline does not hang.

8. CLI interactive test — new fixture dir `cli/tests/fixtures/stage-pause/`, mirroring
   `cli/tests/fixtures/hook-ask/` (`.studio/pipelines/`, `agents/runner.agent.yaml`,
   `contracts/`, `mock.yaml`, `config.yaml`): a two-stage pipeline, stage 1 carrying
   `approval:`, stage 2 with `context.include: [previous_stage_output]` so the test can
   assert what actually reached it. New `cli/tests/integration/stage-pause.pty.test.ts`
   using the existing `runInPty`/`answerEachInTurn`/`stripAnsi` helpers
   (`cli/tests/utils/pty-run.ts`) for the two interactive paths (approve as-is; edit —
   drive the `editor()` sub-prompt by setting `EDITOR` to a short non-interactive script
   that rewrites the temp file directly, so no real keystrokes are needed for the spawned
   editor process). The non-interactive `auto-approve`/`fail` paths are already covered by
   the engine-level test in item 7 and don't need a pty (no TTY branch involved).

9. Docs (same PR, per CLAUDE.md's "Docs to Keep in Sync" table — new YAML key a config
   author can write):
   - `CLAUDE.md` — new "Stage pause (`approval`)" entry in Key Concepts, modeled on the
     existing "Post-validation rejection" entry; add `onStagePause` row to the Events
     System table.
   - `CONCEPTS.md` — matching, more detailed entry.

## Anchoring notes
- Reused: the entire `askHuman`/`onHookAsk` mechanism (decision callback + separate
  observability event, TTY gate, `askQueue` serialization, `withSpinnersPaused`), the
  `parseStageHooks`/`STAGE_HOOK_FIELDS` YAML-parsing pattern, `createTaggingAdapter`
  (already generic, no change needed), `@inquirer/prompts` (already a dependency,
  `editor` prompt already exported, just unused until now), the `hook-ask` CLI fixture
  and pty-test pattern.
- New: `StageApprovalConfig` type, `parseApprovalConfig()`, `StagePauseEvent`/`onStagePause`,
  `reviewStageOutput` callback (engine + CLI), the pause phase in `StageExecutor.execute()`,
  `stage-pause` fixtures and pty test.
- Unverified / assumptions: `ralphResult.result.output` is a plain mutable field (not
  frozen) — will confirm while editing stage-executor.ts; if it turns out immutable,
  reassign `ralphResult.result = { ...ralphResult.result, output: review.output }` instead
  (equivalent effect, one extra line).
- i18n: none (CLI-only English prompts, consistent with the rest of the CLI).
