# Plan — STU-1261: Prove the nested run console on a real run, not only synthetic events

Path: fallback (trivial ticket) — no shaping bundle; planned directly from the issue text and the
real ProgressDisplay/map-orchestrator/call-orchestrator code.
Scope: a committed, runnable `.studio/` fixture that nests two `map` fan-outs (one reached through
a `call`, both live at once under concurrency), plus an integration test that runs it in default,
`--live` and `--json` modes and asserts the console renders both fan-outs correctly.

## Design decision this issue left open

"Whether that is asserted mechanically ... or read once by a human is the design decision."
Chose **mechanical**: this environment has no real TTY, so a human read here would just be me
reading the same captured stdout a test could assert on — making it a test is strictly more value
for the same effort (reproducible, catches regressions, CI-checkable). ora disables spinner
animation on a non-TTY stream, so the captured stdout is the same static text a human would read
piped through `| cat` or in a CI log, not a mess of cursor-movement escapes.

## Changes

1. `cli/tests/fixtures/nested-console/` — new committed fixture (not synthesized per-test, since
   the issue wants something reusable for STU-1260 and future renderer work):
   - `.studio/pipelines/orchestrate.pipeline.yaml` — root, `map: process-books` (depth 0→1,
     concurrency 2) over 2 books, pipeline `book-pipeline`.
   - `.studio/pipelines/book-pipeline.pipeline.yaml` — `call: review-book` → `chapters-pipeline`
     (depth 1→2). This is the "call" the issue's title names.
   - `.studio/pipelines/chapters-pipeline.pipeline.yaml` — `map: review-chapters` (depth 2→3,
     concurrency 2) over that book's chapters, pipeline `chapter-reviewer`. With outer concurrency
     2, both books' inner maps are live at the same time — the actual case STU-861's synthetic
     tests couldn't cover (two live map renderers, not one nested in a linear cascade).
   - `.studio/pipelines/chapter-reviewer.pipeline.yaml` — agent stage `review-chapter` (mock
     provider, contract `verdict`) + script stage `gate-chapter` that fails one specific chapter,
     so the fan-out has a real mixed success/failure result.
   - `.studio/agents/reviewer.agent.yaml`, `.studio/contracts/verdict.contract.yaml`,
     `.studio/mock.yaml`, `.studio/config.yaml`, `scripts/gate-chapter.sh`, `books.input.yaml`.
2. `cli/tests/integration/nested-console.test.ts` — new. Spawns the real CLI three times (default,
   `--live`, `--json`) against the fixture and asserts: both fan-out headers appear (the inner one
   twice, once per book — proving book two's fan-out actually rendered, not just book one's reused);
   inner lines indent deeper than the outer; both inner headers appear before either inner summary
   (proving concurrent liveness, not queued rendering); the gated chapter's failure is a static line
   containing the real error; `--json` contains no human map text and decodes to the expected
   structured output.

## Anchoring notes
- Reused: `nested-call.test.ts`'s call/map YAML shape and script-stage pattern (`executor: script`,
  `runtime: shell`, stdin-JSON `AgentContext`), `run-exit-code.test.ts`'s spawn/waitForExit pattern.
- New: the fixture directory itself (no static `.studio/` fixture convention existed in `cli/tests`
  before this — every other integration test synthesizes its project at run time).
- Findings surfaced while building the fixture (both real, both pre-existing, neither introduced
  here — reported via `toolbox:issues-candidate`, not fixed in this PR, which is scope-limited to
  proving the renderer):
  - `MockProvider`'s `LLMRequest.stage_name` is actually populated from the stage's **contract**
    name (`task.contract_name` in `runner/src/runner.ts`), not the stage's own `name:` — a stage
    with `agent:` but no `contract:` dies with "MockProvider requires stage_name in LLMRequest"
    instead of naming what's missing.
  - In `--live` mode, a stage that transitions directly into a `map` (STU-861's own case) leaves a
    stray frozen "Thinking... (0s)" line above the map's header — cosmetic, not a correctness bug.
- Unverified / assumptions: none — every claim above was reproduced against the real CLI, not
  inferred from source reading alone.
- i18n: none.
